# Study Protocol Template

**适用**：任何「做了一个交互系统 + 要用实证研究验证它」的项目。单次实验室研究、对照实验、课堂 / 田野部署、纵向部署都能套。研究形态在 §3 里声明，不是模板的前提。

**用法**：复制本文件 → 重命名为 `<yourstudy>_protocol.md` → 按 §0 的顺序填 → 删掉所有 `〔…〕` 占位说明和 `例：` 行。

**这份文件填完后同时是两样东西**：
1. **Study protocol**，给 PI / 合作者 / IRB 看；
2. **Dev spec**，§5 和 §6 直接是工程要实现的东西。

模板的核心主张：**系统设计和研究设计是同一份文档的两面。** 系统要记什么、交互按什么顺序走、哪些状态必须可追溯，都由「这份数据要回答哪个问题」决定。分成两份文档写，必然在收数据时才发现某个字段没埋。

---

## 0. 如何填这份模板

### 填写顺序

| 顺序 | 填哪节 | 为什么在这一步 |
| --- | --- | --- |
| 1 | §1 Research Questions | 一切的锚 |
| 2 | §2 Design Goals | 把 RQ 翻译成系统要具备的能力 |
| 3 | §3 研究设计 | 定形态：几组、几次、比什么 |
| 4 | §4 §5 采集清单 | 用户给什么、系统记什么 |
| 5 | §6 原句库 | 把采集项落成用户真正看到的句子 |
| 6 | §7 伦理与数据管理 | 补 IRB 需要的部分 |
| 7 | §8 §9 | 变更日志 + 发布前检查 |

每写下一个采集项，同时写清它回答 §1 的哪个 RQ 或验证 §2 的哪个 DG。说不出来的，删掉。这是挡住「顺手多收一个变量」的唯一办法。

### 三个角色各读哪几节

| 角色 | 读 |
| --- | --- |
| PI / 合作者 / IRB | §1 §2 §3 §6 §7 |
| 工程实现 | §3.4 §5 §6 §8 |
| 做分析的人 | §3 §4 §5 |

### 两条贯穿全文的记法约定

- **采集项编号**：每条数据给一个稳定 ID（`U-` 用户提供，`S-` 系统记录）。§3.4 的时间线表和 §9 的检查清单引用这个 ID，改名时不会断链。
- **可追溯字段**：凡是模型 / 算法产出的数据，都要同时存下产生它的版本号。研究跑到一半改 prompt 或换模型是常态，没有版本号的数据在分析时只能整段丢掉。

## 1. Research Questions

**Overall RQ**: 〔一句话。研究整体在问什么〕

- **RQ1 (〔给它起个短名，例：Prediction / Detection / Accuracy〕)**: 〔具体可回答的问题，能明确指出用什么数据回答〕
- **RQ2 (〔短名，例：Effect / Support / Learning Gain〕)**: 〔同上〕
- **RQ3**: 〔可选。超过三个 RQ 通常意味着该拆成两个研究〕

> 例（学习）：RQ1 系统能多准地从学习者的解题过程与自述推断其掌握度与困惑点？RQ2 自适应提示对学习表现和自我调节学习行为有什么影响？
> 例（情绪）：RQ1 系统能多准地从自述事件推断用户情绪状态？RQ2 AI 生成的引导如何支持用户的情绪调节？

**本节填完的标准**：每个 RQ 都能说出靠哪些采集项回答，而且不止一项。只靠单一数据源支撑的 RQ 太脆弱，那条数据一出问题整个 RQ 就没了。

## 2. Design Goals

把每个 RQ 拆成系统层面的设计目标。DG 是 RQ 和代码之间的那一层，写法是「系统做什么 + 为了什么」，不是「系统有什么功能」。

**RQ1 对应的 DG**

- **DG1 (〔Capture / Input〕)**: 〔系统如何获取原始信号，以及为什么这样设计。注明模态与负担约束〕
- **DG2 (〔Inference / Modeling〕)**: 〔系统如何把原始信号变成内部状态表示。注明理论依据，以及统一的状态表示具体是什么〕

**RQ2 对应的 DG**

- **DG3 (〔Generation / Adaptation〕)**: 〔系统如何从内部状态产出干预内容。注明依据哪套理论选策略〕
- **DG4 (〔Delivery / Presentation〕)**: 〔系统如何把内容交付给用户。注明多通道之间的一致性要求〕

> 例（学习）DG2：以 knowledge-component 模型从作答与自述推断掌握度向量，该向量是提示选择与难度调整的唯一依据。
> 例（情绪）DG2：以 appraisal-based reasoning 推断单一维度估计（valence / arousal / dominance），该估计是所有下游行为的唯一语义来源。

**本节填完的标准**：
- 每个 DG 在 §5 里有对应的可记录、可验证的实现项；
- 存在一个**唯一的内部状态表示**，所有下游模块都从它派生。两条并行的状态来源是后期最常见的不一致源头，也是消融实验做不动的根本原因。

## 3. 研究设计（Study Design）

### 3.1 形态

- **设计类型**：〔between-subjects / within-subjects / 混合 / 单臂部署 / case study〕
- **研究场景**：〔实验室 / 线上远程 / 课堂 / 日常生活中的部署〕
- **时长结构**：〔单次 N 分钟 / 两次间隔 N 天 / 连续 N 天 / 一学期〕
- **交付形态**：〔桌面 web / 手机 web / 原生 app / 嵌在现有平台里〕

> 例（学习）：within-subjects，线上远程，单次 60 分钟，两个 block 内部计数平衡，桌面 web。
> 例（部署型）：单臂，日常生活，连续 14 天，手机 web，每天三个触点。

### 3.2 条件与对照

| 条件 | 系统配置 | 对应哪个 DG / 消融哪个成分 |
| --- | --- | --- |
| 〔C1 baseline〕 | 〔配置〕 | 〔无 DG3 的自适应，固定提示〕 |
| 〔C2 full〕 | 〔配置〕 | 〔完整系统〕 |
| 〔C3 ablation〕 | 〔配置〕 | 〔关掉 DG4 的某个通道〕 |

**条件必须对得上 DG。** 每个条件都是在问「少了这个成分会怎样」。如果某个 DG 在任何条件下都不变，它就没被这个研究验证，要么加条件，要么在 §1 里承认这部分不在本研究范围内。

单臂部署研究在这里写「无对照，以 within-participant 的时间变化 / 与自评基线的对比为比较基准」，并说明这种比较能支持什么、不能支持什么。

- **分配方式**：〔随机 / 分层随机，分层变量是什么 / 计数平衡方案〕
- **盲化**：〔被试是否知道自己在哪个条件，实验员是否知道，评分者是否盲〕

### 3.3 被试与样本量

- **目标人群与纳入 / 排除标准**：〔…〕
- **目标 N**：〔数字〕。依据：〔power analysis 的效应量来源 / 定性饱和 / 同类研究的常规规模〕
- **招募渠道**：〔…〕
- **预期流失率与应对**：〔纵向研究必填〕
- **分析时的排除标准**：〔什么样的 session 或被试剔除。在收数据前定下来〕

### 3.4 任务与流程

被试实际要做的事，按时间顺序：

| 阶段 | 做什么 | 时长 | 产生哪些 U- / S- 数据 |
| --- | --- | --- | --- |
| 〔Consent〕 | 〔…〕 | 〔…〕 | 〔…〕 |
| 〔Baseline 问卷〕 | 〔…〕 | 〔…〕 | U-01 … |
| 〔Calibration / 练习〕 | 〔…〕 | 〔…〕 | U-05 |
| 〔主任务 / 交互 session〕 | 〔…〕 | 〔…〕 | U-10 … S1–S6 |
| 〔Post 问卷〕 | 〔…〕 | 〔…〕 | U-20 |
| 〔访谈〕 | 〔…〕 | 〔…〕 | U-21 |

**重复测量的声明**（有则填）：〔哪些阶段重复、重复几次、每次间隔、触发方式是系统主动还是用户主动〕。

> 例（单次）：主任务重复 2 个 block，每 block 6 题，条件顺序计数平衡。
> 例（部署）：主任务每天出现 3 次。系统推送 1 次（早），固定时段 1 次（晚），用户自发触发不限次但每日上限 8 次。

**负担预算**：〔每个阶段的目标时长〕。写下来，后面每加一项都对着这个预算砍。

## 4. 用户主动提供的数据（Participant-provided）

### 4.1 Baseline / Pre

| ID | 采集项 | 形式 | 用途 |
| --- | --- | --- | --- |
| U-01 | 人口学 | 表单 | 样本描述 |
| U-02 | 〔领域背景 / 先验知识 / 技术使用背景〕 | 表单 or 测验 | 〔协变量 / 分层变量〕 |
| U-03 | 〔量表名 + 题数 + 量程〕 | Likert | 〔moderator〕 |
| U-04 | 〔个性化输入，例：开放式自述 / persona chat N 题〕 | 对话式 | 〔喂给系统做个性化〕 |
| U-05 | 〔Calibration 样本 1 件〕 | 自由输入 + 自评 | few-shot 校准；**不计入 evaluation 数据** |

关于 U-05（calibration）：让被试先做一遍和主任务同构的一小步，同时拿到一个「这个人自己的输入 ↔ 这个人自己的标注」配对样本。三重作用：注入模型做个体校准、充当主任务前的流程练习、暴露 UI 问题。**务必在 protocol 里写明它不计入 evaluation**，否则分析时会被当成第一个正式 trial。

### 4.2 任务中 / 重复测量

| ID | 采集项 | 出现在哪个阶段 | 形式 |
| --- | --- | --- | --- |
| U-10 | 〔自由输入 / 作答〕 | 〔…〕 | 〔语音 / 文字 / 选择〕 |
| U-11 | 〔Before 自评 ×M〕 | 〔…〕 | 〔滑条 / Likert，量程〕 |
| U-12 | 〔After 自评 ×M〕 | 〔…〕 | 同 U-11 |
| U-13 | 〔单题感知确认，例：这个提示贴合吗 / 你觉得它理解你了吗〕 | 〔…〕 | Likert |
| U-14 | 〔条件触发的纠正文本〕 | 〔…〕 | 仅当 U-13 ≤ 〔阈值〕 |
| U-15 | 〔轮换题 / 延迟测量〕 | 〔…〕 | 对话回答 |

**U-14 这类「纠正文本」值得专门设计**：只在被试表示系统猜错时出现，让他说出「正确答案应该是什么」。它同时给你错误案例库和 human evaluation 的 ground truth，成本极低。

**U-15 轮换题（rotating items）**，用于重复次数多的研究：有些问题必须在真实情境里问（被试当下才记得），但每次都问会产生疲劳和 demand characteristics。做法是把这类问题分组按次轮换。在表里写清轮换周期和分组。单次研究不需要这一行，删掉。

### 4.3 Post

| ID | 采集项 | 形式 |
| --- | --- | --- |
| U-20 | Post-study 问卷 〔题数〕 题 | Likert，见 §6.4 |
| U-21 | 半结构式访谈 〔题数〕 题，约 〔分钟〕 | 口头，录音转写 |
| U-22 | 〔客观后测，例：迁移测验 / 保持测验〕 | 〔…〕 |

**问卷题的来源标注是硬性要求**：每题注明是 adapted from 哪个已验证量表，还是 developed for this study。审稿人一定会问，而且写的过程会迫使你发现哪些题其实在重复测同一个构念。

## 5. 系统自动记录的数据（System-logged）

**这一节是 dev spec。** 每个条目都是一条要落库的字段，工程照着实现即可。分成六组，因为它们的失败模式不同：元数据漏了没法对齐，模型输出漏了没法复现，埋点漏了没法讲使用行为的故事。

### S1 · Session 元数据（每次交互）

- [ ] participant ID + session ID + condition + 时间戳（开始 / 结束）
- [ ] 入口 / 阶段类型：〔枚举你的几个阶段或触点〕
- [ ] 输入模态：〔语音 / 文字 / 点选 / …〕，用于 per-modality 分析
- [ ] 会话时长、交互轮数
- [ ] 〔重复测量则记：第几次、在序列中的位置〕（用于分析 order effect）

### S2 · 交互存档

- [ ] 完整交互记录：用户输入 + 系统输出每一轮的双方原文，含每轮时间戳
- [ ] 〔原始媒体的存留决定。例：语音仅存转写文本，不存音频〕

**原始媒体要在 protocol 里明确写「存 / 不存」**，这是 IRB 关心的点，也直接决定存储方案。

### S3 · 模型侧输出

- [ ] 〔推断出的内部状态值〕，**在用户自评之前生成，但在自评完成前不展示**
- [ ] 展示给用户的生成内容原文
- [ ] 〔策略 / 行为标签〕：每轮由模型自标，按 〔哪套理论分类法〕；一次会话可含多种
- [ ] 〔预测性输出，例：post-intervention 状态预测〕，含触发时机与输入范围
- [ ] **本次调用的 prompt 版本号 / 模型 ID / 个性化快照**

两条需要工程特别注意。第一条的顺序是硬约束：一旦让被试先看到系统的猜测再填自评，那一列数据就只能测 anchoring，不能测 accuracy，要为这个顺序写测试。最后一条最容易省掉也最贵：研究中途改 prompt 后，没有版本号的数据无法分段分析。

### S4 · 输出通道状态（每次 session）

- [ ] 〔各交付通道的开关与实际呈现。例：语音播报是否被关掉、视觉通道当时呈现了什么、提示的实际难度等级〕

理由：如果你问了被试「你注意到界面 / 提示的变化了吗」（见 §4.2 U-15），就必须能对上**他当时实际看到了什么**。缺这条，DG4 的分析做不了。

### S5 · 交互质量指标（每次 session）

- [ ] 用户**回复 / 操作**的轮数（不是系统发出的轮数）
- [ ] 总时长、用户每轮输入的长度（字数 / 语音秒数）
- [ ] 结束方式：自然收尾 vs 中途退出
- [ ] 〔自评控件的交互细粒度：每条控件的操作时长、提交前调整次数〕
- [ ] 〔任务型研究补：首次操作延迟、重试次数、求助次数〕

自评控件那条的用处：把「默认值」和「真的选了这个值」区分开，用来检测 straightlining 和疲劳从第几次开始出现。实现要点是**控件初始为未作答态**，不要预置在中点，否则数据里这两种情况无法区分。

### S6 · Engagement / 使用事件（被动埋点）

- [ ] 打开时间点，**含打开但未完成的情况**
- [ ] 用户自发触发的频率与时段分布
- [ ] 漏测 / 未完成记录：哪一次、哪个阶段
- [ ] 模态或功能选择比例随时间的变化
- [ ] 〔模型 / 算法调用失败事件，含当时的回退行为〕

「打开但没完成」和「漏测」是使用行为分析里信息量最大的两类事件，而它们默认不会被任何业务逻辑记下来，必须专门埋。单次实验室研究可简化这一组，但「中途放弃的 trial」仍要记。

## 6. 原句库（Verbatim Copy Deck）

**把被试真正会看到 / 听到的每一句话写在这里，一字不差。** 这节给工程直接复制进代码，也是复现性材料。措辞在 protocol 阶段定稿，不要留给实现时临场发挥。

写法约定：每小节标注 `｜User input：〔输入形式〕`，让工程知道这一句后面接什么控件。

### 6.1 Baseline / Onboarding

**〔分组标题，被试看得到的那个，例：About you〕（表单：下拉 + 填空）**
- 〔字段列表〕

**〔分组标题，例：Your background〕（表单：Likert，1 = strongly disagree … 7 = strongly agree）**
1. _"〔题目原句〕"_
2. _"〔题目原句〕"_

**〔对话式分组〕（〔语音优先、可文字 / 纯文字〕）**
1. _"〔开场问题原句〕"_
   界面提示小点（_"Feel free to touch on any of these"_，被试任选着说）：
   - _〔提示 1〕_
   - _〔提示 2〕_

对话式采集配「提示小点」而不配追问，是为了在不打断叙述的前提下提高覆盖面。追问会让时长不可控，在重复多次的流程里尤其危险。

**〔Calibration 练习〕**
- 输入引导：_"〔原句〕"_
- 自评引导（注意要评**当时**而非当下）：_"〔原句〕"_
- 存储格式：`{〔结构化字段〕}`，推理时以**固定接口**注入，不写进 prompt 文本。这样之后换 prompt 时校准机制不用动。

### 6.2 主任务 / 交互流程

**Step 1 开场｜User input：〔自由输入形式〕**
- 〔阶段 / 触点 A〕：_"〔原句〕"_
- 〔阶段 / 触点 B〕：_"〔原句〕"_

同一个采集项在不同阶段要有不同措辞。被试自发触发时的语气和系统主动推送时的语气不一样，共用一句会很怪。

**Step 2 / Step 4 自评｜User input：〔控件 ×M，量程，是否配图标〕**
- Before：_"〔原句〕"_
- After：_"〔原句〕"_

**Step 3 系统输出｜System output**
- 〔模板结构，含哪些占位符，长度上限〕

**Step 5 〔感知确认〕｜User input：对话回答 + Likert（1–7）**
- 标准版：_"〔原句，含 [模型输出] 占位〕"_
- 软化版（用于 〔哪个阶段〕）：_"〔原句〕"_
- Likert：_"〔原句〕"_
- 仅当 ≤ 〔阈值〕：_"〔原句〕"_

把系统输出插进对话句的时候，**措辞要留出「我可能猜错」的空间**。写成断言，被试会倾向于顺着它改自己的答案，污染后面的自评。

### 6.3 轮换题 / 延迟测量｜User input：对话回答

- 〔主题 1，例：行为采纳〕：_"〔原句，含 [前次内容回顾] 占位〕"_
- 〔主题 2，例：个性化感知〕：_"〔原句〕"_
- 〔主题 3，例：通道感知〕：_"〔原句〕"_

### 6.4 Post-Study Questionnaire｜User input：Likert，1 = strongly disagree … 7 = strongly agree

**Section 1 · 〔构念名〕 — targets RQ1**
1. _"〔题目原句〕"_ —— 〔这题测什么〕
2. _"〔题目原句〕"_ —— 〔这题测什么〕

_〔来源标注：Q1 adapted from 〔量表, 作者 年份〕；Q2 developed for this study。〕_

**Section 2 · 〔构念名〕 — targets RQ2**
〔同上〕

**Section 3 · 〔接受度 / 可用性 / 认知负荷〕**
〔同上。例：TAM 的 perceived usefulness + ease of use 各一题；或 NASA-TLX 子量表〕

每题后面挂一句「这题测什么」，是防重复最有效的手段。两题注释一样，就说明该删一题。

### 6.5 Semi-Structured Interview（约 〔分钟〕）｜User input：口头，录音转写

**Q1.** _"〔开放式总体体验问题〕"_

**Q2.**（RQ1 + RQ2）_"〔关键事件问题。让被试讲一个具体时刻，而不是总体印象〕"_
- Probe: _"〔是什么让它那一刻对了 / 错了？〕"_

**Q3.**（RQ1）_"〔原句〕"_
- Probe（**视该被试的实际数据**）: _"〔原句，例：我们注意到你后半段的评分上升了，你自己感觉到这个变化了吗？〕"_

**Q4.**（RQ2）_"〔行为层面：你实际用了哪些？什么有用、什么没用、为什么？〕"_
- Probe: _"〔反向探询：有哪些你觉得合理但没去做？是什么阻止了你？〕"_

**Q5.**（RQ2）_"〔元认知变化：用了之后你对自己的 〔构念〕 的注意方式有变化吗？〕"_

**Q6.** _"〔最有用 / 最无用〕"_
- Probe（DG4）: _"〔通道感知〕"_
- Probe（DG1）: _"〔负担感知〕"_

**Q7.** _"〔兜底开放题〕"_

访谈设计的两个要点：**数据驱动的 probe**（Q3）要求访谈前先看该被试的日志，这是带系统日志的研究能做而纯问卷做不到的事；**反向探询**（Q4 probe）问「为什么没做」，通常比「做了什么」信息量更大。

## 7. 伦理与数据管理

- **IRB / 伦理审批**：〔编号与状态〕
- **知情同意**：〔形式、何时、是否可撤回及撤回后的数据处理〕
- **采集到的敏感数据类别**：〔逐项列出，对齐 §4 §5〕
- **原始媒体存留决定**：〔存 / 不存，及理由。对齐 S2〕
- **去标识方案**：〔ID 与真实身份的映射存在哪、谁能访问〕
- **存储与保留期**：〔位置、加密、保留多久、何时销毁〕
- **第三方服务**：〔数据会经过哪些外部 API，对应的条款与地域〕
- **风险与应对**：〔例：被试表露风险信号时的处置流程与转介资源〕
- **补偿**：〔金额、发放条件、是否与完成率挂钩〕

补偿与完成率的挂钩方式要写清。按次结算和按完成度结算会产生完全不同的使用行为数据，分析 engagement 时必须把这个制度因素说明。

## 8. 变更日志（Protocol Changelog）

| 日期 | 改了什么 | 影响哪些数据 | 版本号 |
| --- | --- | --- | --- |
| 〔YYYY-MM-DD〕 | 〔改动〕 | 〔哪些被试 / 哪几次的数据受影响〕 | 〔v〕 |

研究跑起来之后一定会改东西。这张表决定了分析时能不能把前后两段数据合起来用。prompt、措辞、流程的任何改动都登记在这里。

## 9. 发布前检查清单

**协议完整性**
- [ ] §1 的每个 RQ 都能说出靠哪些采集项回答，而且不止一项
- [ ] §2 的每个 DG 在 §5 有对应的可记录实现项
- [ ] §3.2 的每个条件都对应一个 DG 的消融
- [ ] §3.3 的排除标准已在收数据前定稿
- [ ] §4 §5 的每个 ID 都能说出它回答哪个 RQ 或验证哪个 DG
- [ ] §6.4 每题都有来源标注和「测什么」注释
- [ ] 负担预算（§3.4）与原句库的实际长度相符

**实现正确性**
- [ ] 推断值在自评完成前不展示，并且有测试覆盖这个顺序
- [ ] 未作答态与中点值在数据里可区分
- [ ] 模型产出都带版本号
- [ ] 条件分配、漏测、中途退出、调用失败四种情况各跑通一次

**端到端**
- [ ] 自己完整走一遍全部阶段，含 consent 和 post
- [ ] 找 〔2–3〕 人做 pilot，之后再锁 §6 的措辞
- [ ] **导出一次 pilot 数据**，逐条核对 §4 §5 的采集项是否真的落了库、能不能对齐到同一个 session

最后一条价值最高。pilot 之后不导数据、不实际拿导出的字段算一遍，等到正式数据收完才发现某个字段没埋或对不上，是最常见也最无法挽回的失败。
